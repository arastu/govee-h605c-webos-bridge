# Govee H605C ambilight from a rooted LG webOS TV (no camera)

Screen colours are captured on the TV and pushed to the Govee strip over the TV's own
Bluetooth. No Govee camera, no Raspberry Pi, no extra hardware.

```
PicCap (hyperion-webos)  --flatbuffers:19400-->  HyperHDR (on the TV)
HyperHDR "udpraw" device --udp 127.0.0.1:19446--> bridge.js (node, on the TV)
bridge.js --luna com.webos.service.bluetooth2 gatt/writeCharacteristicValue--> Govee H605C (BLE)
```

## Why Bluetooth
The H605C has no Govee LAN API (verified: no reply on UDP 4001/4003), so the only local
real-time path is BLE. The TV's `com.webos.service.bluetooth2` service exposes a GATT client
(`gatt/connect`, `gatt/discoverServices`, `gatt/writeCharacteristicValue`), usable from a
root shell or a Node script on the TV.

## Govee BLE facts (H605C, firmware 1.01.00)
- Advertises as `Govee_H605C_3662`, BLE address `d7:37:32:32:36:62`.
- Service `00010203-0405-0607-0809-0a0b0c0d1910`, write char `...2b11`, notify char `...2b10`.
- Frames are 20 bytes: 19 bytes of command padded with zeros + XOR checksum. No encryption.
- Power `33 01 01/00`, brightness `33 04 <1..100>`, heartbeat `AA 01`.
- Colour for a set of segments: `33 05 15 01 RR GG BB 00 00 00 00 00 <mask lo> <mask hi>`
  (bit i = segment i, LSB first; `FF 7F` = all 15 segments).
- `AA 40` reports 72 ICs (216 LEDs / 3).

## webOS specifics (webOS 4.10, bluetooth2)
- `gatt/connect` must stay subscribed; the link drops when the caller exits.
- The write call takes `appId` (returned by connect), not `address`:
  `{"appId":N,"service":"...1910","characteristic":"...2b11","writeType":"noresponse","value":{"bytes":[...]}}`
- Node on this TV is v0.12; use `NODE_PATH=/usr/palm/nodejs:/usr/lib/node_modules` and an
  anonymous `palmbus.Handle('')`.

## Files
- `bridge.js`   the bridge service (ES5, node 0.12)
- `config.json` BLE address, segment count, UDP port, grouping thresholds, `reverse`/`offset`
  to fix segment orientation
- `run.sh`      start/stop helper (`./run.sh start|stop`)
- `init.d-govee-ambilight` boot hook, installed as `/var/lib/webosbrew/init.d/50-govee-ambilight`

On the TV the files live in `/media/developer/govee-bridge/`. Log: `/tmp/govee-bridge.log`.

## HyperHDR settings applied (web UI: http://<tv-ip>:8090, password `hyperhdr`)
- LED device: `udpraw`, host `127.0.0.1`, port `19446`, colour order RGB
- LED layout: built from MEASURED corner positions in LED units (216 LEDs, 15 segments of
  14.4). Strip starts at the bottom-right corner, up the right side, right-to-left along the top,
  down the left side, left-to-right along the bottom. Corners (LED index from strip start):
  right->top 43.2, top->left 104.2 (segment 7 spills 11 LEDs onto the left edge), left->bottom
  147.4 (assumed equal to the right side), end at the bottom-right corner. The strip is four pieces
  joined by corner cables, so sides are not proportional to the TV size.
  Generated by `python3 layout.py 15 216 43.2,104.2,147.4`.
- Smoothing: 20 Hz, 200 ms

## PicCap settings applied
address `127.0.0.1`, port `19400`, fps 15, vsync off, **320x240** (this TV's scaler cannot go below
320x240; at 320x180 PicCap sends empty 0x0 frames), backend auto (dile_vt + gm on this TV), autostart on.

## HyperHDR database
HyperHDR keeps its settings in `/home/root/.config/HyperHDR/db/hyperhdr.db` and did a one-time
"table upgrade" that reset the device/LED settings on its second start. A known-good copy is kept
at `/media/developer/govee-bridge/hyperhdr.db.good`; if the device ever shows as `file` again,
stop HyperHDR, copy it back, start HyperHDR.

## Operating
- Restart bridge: `/media/developer/govee-bridge/run.sh start`
- Stop everything: `run.sh stop`, `luna-send -n 1 luna://org.webosbrew.piccap.service/stop '{}'`,
  `luna-send -n 1 luna://org.webosbrew.hyperhdr.loader.service/stop '{}'`
- Close the Govee Home app while the bridge runs: the strip accepts one BLE client at a time.
